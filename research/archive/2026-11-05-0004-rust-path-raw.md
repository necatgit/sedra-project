## Summary

1. **Fork base: kaspad Go `v0.12.15` (`5a3b8a00`). Verified.** After normalizing renames, Sedra's first code commit differs from v0.12.15 by 580 changed lines, against 610 to 8,302 lines for every other candidate. All 580 are renames, params, genesis and vendored modules.
2. **Sedra's consensus divergence from Kaspa is small and fully enumerable. Verified.** It consists of the genesis block, network name, address prefixes and ports, a different subsidy table from month 8 on (192 entries, changed in 2025-04), the v2.0.0 difficulty reset (DAA [53,625,512, +2641)), and the v2.0.0 treasury coinbase outputs (two windows). After normalization, the PoW (kHeavyHash), hash domains, GHOSTDAG, DAA, pruning, pruning proof, mass and txscript code are byte-identical to kaspad v0.12.15 (zero non-comment diff lines).
3. **The Rust hashing rules reproduce Sedra's mainnet genesis hash `7c380ae6…5ffa`. Verified.** I used a stdlib Python reimplementation of rusty-kaspa v1.0.1's header, tx and merkle hashing. A control case reproduced the Kaspa devnet genesis first.
4. **Latest rusty-kaspa (v1.1.0 and later, v2.1.0, master) is the wrong base for Step 1. Verified.** After v1.0.1, Kaspa deleted the pre-Crescendo (1 BPS, Go-compatible) consensus paths: the legacy full-window difficulty manager (`e2ce9a63`), the GHOSTDAG k switch, the pruning v1 methods (`189dda69`, `3c2115d9`, `3ba06589`). It also deleted P2P v5 (`f25a737b`) and moved to Toccata (block version 2, P2P 10/11). Sedra runs exactly those deleted rules.
5. **rusty-kaspa `v1.0.1` is the natural base. Inferred.** It still has the full pre-Crescendo consensus behind `crescendo_activation`, which can be set to `ForkActivation::never()`. It also still contains the P2P v5 flows. Its mainnet gate rejects v5 since `255b3fd5`, but that gate is a one-line condition (`flow_context.rs:785@v1.0.1`). The trade-off: it is 249 commits behind, has no upstream maintenance on this line, and security fixes would need manual backports.
6. **zkas-rusty is not a sensible base for Step 1. Verified.** Its root tree equals rusty-kaspa `98a4ccd8` (post-Toccata, post-cleanup), so it lacks the legacy rules too. On top of that it adds 485 files (+250,905/−2,333), mostly Zcash/Orchard shielded code (148,701 lines under `patches/` alone). The AuxPoW core is about 1.2k lines (`consensus/core/src/auxpow.rs`, `consensus/pow/src/auxpow.rs`, plus header, p2p and merkle glue) and could be ported into a v1.0.1-based Sedra node.
7. **Go-vs-Rust discrepancy found: the minimum difficulty window. Verified.** Go (inherited from kaspad) returns genesis bits while the window has fewer than 2641 blocks. Rust v1.0.1 does so only below `min_difficulty_window_size = 150`. This only affects blocks near genesis, but a from-genesis Rust validation of Sedra would reject such blocks unless the parameter is set to 2641.
8. **Syncing next to Go nodes. Inferred.** IBD is plausible: the gRPC service path, protobuf field numbers and handshake semantics are unchanged, and Kaspa's own Rust nodes synced from Go peers via v5. Two things are still to prove: the v2.0.0 rules are below the current pruning point, so a pruning-proof IBD will not exercise them, and whether a full from-genesis validation is possible at all is **Unknown** (see 9).
9. **Open risk: the 2025-04-08 subsidy-table change (`e61214d`) may have been retroactive. Unknown.** It replaced table entries from month 8 on (DAA ≥ 36,558,000). If the chain had already passed that DAA, historical coinbases follow the old table and no single table validates the whole chain. Only real chain data can settle this.
10. Nothing here shows that the AuxPoW fork (Step 2) is safe or decided. This research only maps the work and the checkpoints.

#### 3b. Rusty-kaspa features that kaspad 0.12.x never had (must stay off)

At v1.0.1 these are all gated by the single `crescendo_activation: ForkActivation` (`params.rs:257`, mainnet value `ForkActivation::new(110_165_000)` at `:541`). `ForkActivation::never()` = `u64::MAX` (`params.rs:16-30`). **Verified** gates in v1.0.1 (`git grep crescendo_activation`):
- storage mass / KIP-9 (`consensus/mod.rs:833`, `virtual_processor/processor.rs:1075`);
- body checks (`body_validation_in_isolation.rs:14`);
- header post-PoW checks (`post_pow_validation.rs:58,87`);
- UTXO validation / KIP-10 and the sequencing commitment (`utxo_validation.rs:183,259,266,461`);
- tx header context (`tx_validation_in_header_context.rs:97`);
- sampled vs full difficulty (`difficulty.rs:320`);
- BPS-dependent subsidy (`coinbase.rs:248-258`);
- the 10-BPS `CrescendoParams` (`params.rs:143-185`).

Tests in `coinbase.rs:378,445` already construct `never()`.

**Inferred:** with `never()`, v1.0.1 runs the exact rule set Kaspa mainnet ran with v1.0.0/v1.0.1 before 2025-05-05. That pre-activation path was production-tested on Kaspa mainnet with Go and Rust nodes coexisting. Residual risk: code that assumes activation is eventually reached, such as countdown loggers. Not exhaustively audited.

Later KIPs (KIP-16, KIP-17, covenants, multidimensional mass, Toccata tx version 1 / block version 2, KIP-21, ZK opcodes) exist only after v1.0.1 (commit log, Evidence E6). They are therefore absent from a v1.0.1 base. **Verified** by commit dates against tag ancestry (`git merge-base --is-ancestor`).

### Q4. Compatibility with the existing chain

- **P2P v5. Verified:**
  - Last tag that accepts v5 on mainnet unconditionally: `v0.17.2` (`flow_context.rs:780-781@v0.17.2`).
  - `v1.0.0`: v5 accepted until one day before Crescendo (`flow_context.rs:784-800@v1.0.0`, from `3f192d04`). With `crescendo_activation = never` it stays accepted.
  - `v1.0.1`: `connect_only_new_versions = network_type != Testnet` (`flow_context.rs:785@v1.0.1`, from `255b3fd5` 2025-05-07). v5 is therefore rejected on mainnet, but the v5 code is present (`:796`). Re-enabling it is a one-line condition change.
  - `f25a737b` deleted `protocol/flows/src/v5/mod.rs` (155 lines) and `v5/request_pruning_point_and_anticone.rs` (117), plus the consensus APIs `get_daa_window` and `get_trusted_block_associated_ghostdag_data_block_hashes`. These are marked "Delete this function once there's no need for go-kaspad backward compatibility" (`consensus/core/src/api/mod.rs@4826b38f`). It moved the rest to `v7/`. 24 files, +22/−355. First tag without v5 code: `v1.1.0` (2026-03-04).
  - **Inferred:** restoring v5 on HEAD is not just reverting 355 lines. HEAD also changed headers (compressed parents `73c6d5d2`, header chunking `f2f87ff6`), IBD and tx fields after `f25a737b`.
- **Handshake. Inferred (Verified code on both sides):**
  - Go accepts peers advertising a higher version and runs at its own max of 5 (`receiveversion.go:80-110`, `UpdateFieldsFromMsgVersion`).
  - Rust v1.0.x registers v5 flows when the peer advertises 5.
  - The network name must match exactly (`receiveversion.go:70`, `flow_context.rs:778@v1.0.1`).
  - Kaspa's v5 flows contain explicit Go-peer handling ("previous version peers (especially golang nodes)…", `protocol/flows/src/v5/ibd/negotiate.rs:15@v1.0.1`; "deprecated also in go-kaspa", `v5/mod.rs:150`).
- **Header/block serialization and hashing. Verified:**
  - Rust header hashing "emulates bigint.bytes() in the kaspad golang ref" (`consensus/core/src/hashing/mod.rs:31@v1.0.1`).
  - P2P header conversion "follow[s] the golang specification" (`protocol/p2p/src/convert/header.rs:24,55@v1.0.1`).
  - My reimplementation of the v1.0.1 hashing reproduces both Kaspa devnet's and Sedra mainnet's genesis hash and merkle root (E3).
  - Sedra changed none of the Go serialization or hashing code (C14).
- **Pruning proof format.** Not separately verified by me. **Inferred** to be compatible because v5 IBD (pruning proof, pruning point + anticone with trusted data, UTXO set chunks) in rusty-kaspa was built to sync from Go kaspad, and Sedra's Go pruning, pruning-proof and protowire code is unmodified kaspad v0.12.15 (C14).
- **Rules that a pruning-proof IBD will not exercise. Inferred:** pruning depth is 185,798 DAA (~2.15 days at 1 BPS). The v2.0.0 windows end at DAA 53,633,721 (2026-08). Trusted blocks skip body-in-context validation ("body validation in context is not called for trusted blocks", `body_validation_in_context.rs:74@v1.0.1`). A new Rust node syncing today will therefore never run C9/C10 on real data. Those rules need their own test vectors (milestone M6). The current tip DAA is **Unknown** (not queried).
- **Documented Go-vs-Rust differences found in rusty-kaspa v1.0.1 (Verified, `git grep -i golang|go-kaspad`):**
  - consensus-relevant: the tx size limits "technically a soft fork" (`params.rs`); the min difficulty window (my finding above, not labelled in Kaspa's code);

- **Databases** are not shared (Go LevelDB vs Rust RocksDB). Nodes interoperate only over P2P. **Verified** (go.mod lists goleveldb; rusty-kaspa uses rocksdb). No consensus impact.

### Q7. Risks

- **R1. Retroactive table change (Unknown).** If `e61214d` applied to months that had already been mined, the chain contains coinbases from two tables. A from-genesis validation would then need a DAA-gated table switch whose activation point is not documented. Pruning-proof IBD sidesteps it, but it limits verifiability claims.
- **R2. sedracoin/go-muhash v1.0.1 and go-secp256k1 v1.0.2 (Unknown).** If these differ from upstream (MuHash domains, Schnorr/ECDSA rules), UTXO commitments or signature validation diverge. M7 catches the MuHash part.
- **R3. Maintenance burden of a v1.0.1 base (Inferred).** No upstream fixes. Every later Kaspa security fix needs triage. Later rebasing onto modern rusty-kaspa means re-adding legacy rules.
- **R4. Hidden activation assumptions in v1.0.1 (Inferred).** Kaspa ran the pre-activation path only for a finite period. A permanent `never()` may hit code that assumes the fork eventually happens.
- **R5. Difficulty-reset silent fallback (Verified in Go).** Go keeps the computed bits if the DAA score read fails (`difficultymanager.go:163-166`). Rust must match the observable result, not that failure mode. Whether the fallback ever fired on mainnet is Unknown.
- **R6. Coinbase output limit in treasury windows (Inferred).** Go builds blue outputs + red output + treasury output under a K+2 = 20 limit (`transaction_in_isolation.go:134-136`). A block with 19 rewarded blues, a red reward and the treasury output would exceed it. The comment says only 163/200 and 400/454 window slots carried outputs; why is Unknown. Rust must reproduce Go behaviour exactly, including any such rejection.
- **R7. AuxPoW parent format drift.** Kaspa headers moved to version 2 with compressed parents (Toccata). The Sedra verifier must track Kaspa's live format while Sedra's own format stays on version 1.
- **R8. Kaspa coinbase payload budget.** 204 bytes on Kaspa mainnet (`params.rs:614@4edcbbcc`). ZKas's `ZKM1` tag is 4 + 64 hex bytes. A Sedra commitment next to it and the pool's own data must fit. Unknown how much space pools have left.
- **R9. Governance and tooling.** Sedra's Go node becomes legacy. Mining-pool stratum (Miningcore) and explorers talk RPC; the Rust node's RPC is gRPC/wRPC with Kaspa-style schemas but different method details from Go. This needs an RPC compatibility check for Miningcore. Not reviewed here.
