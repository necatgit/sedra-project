## Summary

1. **Verified**: the relaunch branch adds **16 commits** on top of `main` (`e61214d`), not 57 (57 is the total commit count of
   the branch including history). They are dated 2026-08-04 to 2026-08-11, by "Sedra Relaunch", "minerdev95" and "sedra";
   every one carries a `Co-Authored-By: Claude Opus 4.8` trailer. None is GPG-signed. Tag `v2.0.0` is a lightweight
   (unsigned, non-annotated) tag pointing at the branch head `4a1153d`.
2. **Verified**: there are exactly **two consensus rule changes**, both gated on the block's own DAA score and both already in
   the past: (a) a fair-restart **difficulty reset** forcing genesis difficulty for DAA scores [53,625,512, 53,628,153);
   (b) a **treasury allocation** adding one extra coinbase output to a fixed P2SH address for DAA scores in
   [53,632,372, 53,632,572) at 10,000,000 SDR per output and [53,633,267, 53,633,721) at 1,000,000 SDR per output. Nothing is
   scheduled for a future DAA score. The P2P protocol version (5), PoW, header format, mass and subsidy rules are unchanged.
3. **Verified (code comment and commit message, not independently counted on chain)**: the developers state the treasury mint
   was 163 x 10M + 400 x 1M = **2,030,000,000 SDR**, i.e. 30M SDR above the 2B target, because the number of outputs depends on
   how many *chain blocks* fall in the DAA window, which could not be known in advance.
4. **Verified on chain**: the treasury address is a **plain 2-of-3 multisig with no timelock**. The redeem script revealed in
   its spending transactions is `OP_2 <key1> <key2> <key3> OP_3 OP_CHECKMULTISIG`, and its BLAKE2b-256 hash equals the script
   hash hardcoded in consensus. The code comments and commit messages describing it as "CLTV-timelocked" with vesting
   "enforced by the CLTV timelock on the script" are **not accurate for this address**. Consensus enforces no vesting.
5. **Verified on chain**: treasury balance now **32,931,757.98 SDR** (43 UTXOs, all change outputs from spends). Compared with
   the stated 2.03B mint, about **1.997B SDR have left the address**. Only 16 outgoing transactions (228,322,485 SDR to 7
   pubkey addresses) are visible, because the explorer's transaction index is stale (`/info/health` returns
   `"Transactions not up to date"`). Where the remaining ~1.77B went is **Unknown** from the public API.
6. **Inferred, needs an answer from the developers**: the node-reported circulating supply (26,681,754,447 SDR at DAA
   61,118,652) is about **8.03B SDR higher** than the published code's subsidy schedule can have emitted up to that DAA score
   (upper bound about 18.65B). The 2.03B treasury explains part of it; about **6.0B SDR (to within ~100 SDR) is not explained
   by any code in the repository**. It is also above the total lifetime schedule of the code (about 22.79B + 2.03B).
   This is an arithmetic model with stated assumptions, not proof of wrongdoing; see Finding 3.6.
7. **Verified**: mainnet reports `serverVersion: 2.0.0-relaunch`. Every commit from `efb5187` onward builds that same string
   (`appBuild=relaunch`), so the version string cannot prove which commit, or whether published code at all, mainnet runs.
8. **Verified**: the rules were changed while the chain was running: window 1 was armed (39417d6), then *replaced* by window 2
   (f58dcb0) after window 1 under-delivered, then both were restored as a list (4a1153d) because a fresh node "would reject
   the first-window coinbases during IBD and fail to sync". Commit f58dcb0 is therefore a build that cannot validate mainnet.
9. **Inferred**: for a merged-mining fork, base on `v2.0.0` / `4a1153d` (the only published code consistent with mainnet), reuse
   the DAA-score gate pattern (`block's own DAA score`, shared by builder and validator), but bump the P2P protocol version,
   embed the commit hash in the version, and never derive an amount from "blocks per DAA window".

### Q2. How activation works

- **Verified**: activation is by the **block's own DAA score**, read from `daaBlocksStore.DAAScore(blockHash)`
  (`difficultymanager.go:163`, `coinbasemanager.go:232`). Both windows are half-open `[activation, activation + window)`.
  There is no virtual-score or wall-clock gate, no version bit, no signalling.
- **Verified**: in the validation path the DAA score is staged *before* the check (`StageDAADataAndReturnRequiredDifficulty`
  calls `stageDAAScoreAndAddedBlocks` and then `applyDifficultyReset`, `difficultymanager.go:85-100`). The template path calls
  `RequiredDifficulty(VirtualBlockHash)` (`block_builder.go:280`, `consensus.go:708`), i.e. it uses the virtual's DAA score,
  which is the DAA score the new block will have.
- **Verified** (commit `522475f` message): the title "correct difficulty-reset activation to virtual DAA score" means the
  *value* was chosen as the virtual's DAA score at resume time (stored tip 53,625,511, virtual 53,625,512) so the first new
  block is inside the window; the first attempt (53,625,513) "left the first block at the old hard difficulty (unmineable)
  -> chain stuck. Found by live rehearsal on the restored chain."
- Exact values and effects (**Verified** from `params.go:289-301`):
  - DAA 53,625,512 to 53,628,152 inclusive: required difficulty = genesis bits (genesis difficulty; the test edit in
    `62e18c5` describes this as "830 H/s"). Afterwards normal DAA resumes from that window.
  - DAA 53,632,372 to 53,632,571 inclusive: each block's coinbase must contain an extra 10,000,000 SDR output to the treasury.
  - DAA 53,633,267 to 53,633,720 inclusive: same with 1,000,000 SDR.
- **Verified**: current virtual DAA score was 61,118,652 (`/info/blockdag`, 2026-11-05 15:20 UTC). All three windows ended
  about 7.48M DAA ago. **Nothing in this code is dormant-but-scheduled for a future DAA score on mainnet.**
- **Verified**: `applyDifficultyReset` silently returns the unmodified bits if the DAA score lookup fails
  (`difficultymanager.go:163-166`). **Inferred**: harmless in the paths above because the score is staged first, but a
  swallowed error in consensus code is a fragile pattern.

### Q6. Implications for a merged-mining (AuxPoW) fork

- **Inferred**: base on tag `v2.0.0` / `4a1153d`. `main` cannot follow mainnet (C1 and C2 are hard forks), and `f58dcb0` cannot
  sync. Ask the developers to confirm that mainnet binaries are built from `4a1153d` (Q7).
- Pattern to reuse (**Verified** in code): a pure gate function on the block's own DAA score, evaluated in the shared path used by
  both template building and validation (`blockInDifficultyResetWindow`, `blockInTreasuryAllocationWindow`), wired via
  `dagconfig.Params` -> `consensus.Config` -> manager constructors, dormant when unset. For AuxPoW use an open-ended
  `daaScore >= activation` gate, not a window.
- Pitfalls learned here:
  - Set activation from the **virtual** DAA score at arming time plus a margin; `522475f` shows an off-by-one stalled the chain.
  - Never size anything by "blocks in a DAA window" (only chain-block coinbases count).
  - Keep every past rule (both treasury windows, the reset window) in the params forever, or IBD breaks (`4a1153d`).
  - **Inferred**: AuxPoW changes header validation and PoW (`IsValidPoW`, header serialisation, pruning proof, RPC block
    template and submit), which this relaunch did **not** touch. It is a much larger change than C1 or C2 and has no precedent in
    this codebase.
  - Bump the P2P protocol version (`receiveversion.go:21-23`) or add a minimum peer version so pre-fork nodes disconnect
    loudly, and put the commit hash into `appBuild` so `serverVersion` identifies the build.
  - Publish signed tags and reproducible build hashes; the current script is not reproducible across machines.
  - This is a Go (kaspad-lineage) node. ZKas AuxPoW lives in Rust (`rusty-kaspa` lineage). **Inferred**: ZKas code cannot be
    cherry-picked; it must be ported.
