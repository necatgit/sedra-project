# Release checklist: sedra-rusty v0.1.0 (2026-11-14)

The first public release of the Rust Sedra node (step 1: exactly Sedra mainnet's current rules, no merged mining) and
the start of the first public node of this project. The build and verification recipe itself is in sedra-rusty
`docs/RELEASE.md`; this list is the order of the day and what has to be ready before it.

Who: **Nec** = decisions, GitHub settings, router and Proxmox. **AI** = everything else, each step reported.
Status: `[ ]` open · `[x]` done · `[-]` dropped

## Decisions needed before release day

- [x] **D1 Re-soak of the release binary.** M9 tests commit `210a906`. The release adds the optional back-ports and
      the release preparation (version string, reproducible build). Recommended: run the release binary next to the Go
      node for 24 h before announcing it (same comparison script); the tag and the binaries can be published at once,
      the announcement waits. Alternative: announce directly, since every added change is tested and none touches
      consensus.
- [x] **D2 Tag signing.** Unsigned tag (verification by rebuilding only), or a signing key for Nec's identity
      (SSH or GPG, kept off the build machines). Recommended: SSH signing key, created by Nec, public part in the
      repository's `docs/RELEASE.md`.
- [x] **D3 The public node's role.** P2P only (recommended to start: serves blocks and peers, nothing else), or also a
      public RPC for wallets and explorers (more useful, more attack surface: needs rate limits and `--utxoindex`).

**Decided by Nec on 2026-11-10:**
- D1: the M9 tests are trusted. The 24 h comparison of the release binary runs, but in parallel: it does not block
  publishing or the announcement. A difference found in it is handled like any bug (fix, 0.1.1).
- D2: an SSH signing key for Nec, verifiable on puddlepool.com (public key and fingerprint published there, in
  `docs/RELEASE.md` and as a signing key on Nec's GitHub account). Nec creates it and keeps the private key; Nec runs
  the one signing command on release day, so the key never sits on a build machine unattended.
- D3: P2P connections only, as a start. RPC stays bound to localhost.

## Before release day (preparation)

- [ ] **P1 Container build on two machines** with the current `dev`: `contrib/reproducible/build-in-docker.sh` on the
      dev box (WSL) and on the test VM; both `SHA256SUMS` must match. Done early so that a mismatch is found and fixed
      before the release, not on the day. Result into `docs/RELEASE.md` ("How far this has been tested").
- [ ] **P2 History scan of sedra-rusty** before it becomes public: no private IP addresses, host names, real names,
      private e-mail addresses, keys or tokens in any commit (all branches that will be pushed). Fix by new commits
      where possible; anything that needs a history rewrite goes to Nec first.
- [ ] **P3 Public face of the repository:** README for outsiders (exists), `SECURITY.md` with a contact for
      vulnerability reports, repository description and topics, issues enabled, branch protection on `dev`/`main`.
- [ ] **P4 Release notes draft:** what the node is, what it is not (no merged mining, no fork), the test evidence
      (M1-M9, wallet test, test counts), how to verify, known limits (binary name `kaspad`, Linux amd64 only).
- [ ] **P5 Public node prepared on the test VM:** systemd unit for the release binary (data directory on its own
      disk, restart policy), firewall rule for the P2P port only, the RPC port bound to localhost. Not started yet.
- [ ] **P7 Signing key (D2):** Nec creates the key; its public part goes to puddlepool.com (`/keys/`), to
      `docs/RELEASE.md` with the fingerprint and to Nec's GitHub account; a test tag is signed and verified once.
- [ ] **P6 Merge rehearsal:** `optional-backports` is not based on the current `dev`; merge it into a scratch branch
      and run the full suite now, so release day only repeats a known-good merge.

## Release day, 2026-11-14

1. [ ] **07:20 UTC, M9 ends.** Read the final summary on the test VM; post the final comment on #28 and close it
       (closing issues needs Nec's OK on the day). A single alert or state difference stops the release until
       explained.
2. [ ] **Merge** `optional-backports` into `dev` (as rehearsed in P6), full test run, result recorded.
3. [ ] **Release commit:** `sedra_release` stays `0.1.0`; Nec signs the tag `v0.1.0` (D2); verify it with the published key.
4. [ ] **Build** with `build-in-docker.sh` on both machines; `SHA256SUMS` must match. A mismatch stops the release.
5. [ ] **Smoke tests with the release binary** on the test VM: `kaspad --version` shows `0.1.0` and the tagged commit;
       sync from the **local Go node only** (never from production, see the 2026-11-06 freeze); wallet test
       (`tools/e2e-merged-mining/wallet_test.sh` with the release binary).
6. [ ] **Publish:** Nec makes `sedra-rusty` public; push the tag; GitHub release with the archive, `SHA256SUMS` and the
       release notes; open the release issue inviting independent rebuilds.
7. [ ] **Public node:** Nec renames the VM (Proxmox and hostname) and opens the P2P port on the router; AI installs the
       release binary as a service and checks that outside peers connect. The 24 h comparison (D1) starts here and
       runs in parallel; it does not hold up step 8.
8. [ ] **Announce and document:** README status, ROADMAP (#30 public node), SIP-0002, an `updates/` post, TIMELINE;
       inform the Sedra team (operators can now run an independent node). Close #29 (back-ports) if nothing remains.
9. [ ] **Then:** the treasury trace (an archival node, after M9 as planned) and the public testnet plan (#13).

## If something goes wrong

- Checksums differ across machines: no release; investigate (`docs/RELEASE.md`, "If your checksum differs").
- A test fails after the merge: release without the optional back-ports (the soaked state plus release preparation),
  back-ports in 0.1.1.
- The public node misbehaves: stop its service; nothing else depends on it yet. The pool keeps using its Go node.
